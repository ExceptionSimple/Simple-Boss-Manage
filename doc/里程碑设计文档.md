# 里程碑设计文档

- 日期：2026-10-27
- 操作人：lovexiaoling
- 状态：已确认，进入实现

## 1. 目标

里程碑相当于一个独立账号 / 工作区。用户可以创建多个里程碑，每个里程碑拥有完全独立的一套投递数据；不同里程碑之间互不可见。用户先创建里程碑，再在该里程碑下同步、编辑、发消息；点击「保存里程碑」后，该里程碑被冻结，所有数据变为只读。

## 2. 核心规则

1. 里程碑自动编号：M1、M2、M3……
2. 同一时间只允许一个里程碑处于「编辑中」（active）。
3. 新建里程碑时，若已有编辑中的里程碑，系统先自动保存（冻结）它，再创建新的里程碑。
4. 已保存的里程碑永久只读，不提供解冻入口。
5. 所有业务数据按里程碑隔离，选择哪个里程碑就只看 / 只操作哪个里程碑的数据。
6. Cookie、API Key、消息方案等全局配置不隔离，所有里程碑共用。
7. 冻结校验在后端强制执行，前端禁用按钮只是体验层。

## 3. 数据模型

新增 `milestones` 表：

| 字段 | 类型 | 说明 |
|------|------|------|
| id | INTEGER PK AUTOINCREMENT | 里程碑 ID |
| name | TEXT UNIQUE NOT NULL | M1、M2…… |
| status | TEXT NOT NULL | active（编辑中）/ frozen（已保存） |
| created_at | TEXT | 创建时间 |
| frozen_at | TEXT | 保存时间，未保存为空 |

业务表新增 `milestone_id INTEGER NOT NULL`：

| 表 | 约束调整 |
|----|---------|
| bosses | 去掉 encrypt_boss_id 全局唯一，改为 UNIQUE(encrypt_boss_id, milestone_id) |
| job_info | 主键改为 (id, milestone_id) |
| chat_messages | 主键改为 (id, milestone_id) |
| sync_logs | 新增 milestone_id，加索引 |
| message_failed_queue | 新增 milestone_id，加索引 |
| config | 不隔离 |

同一 BOSS 在不同里程碑中可以各自存在一条记录，聊天记录也各自独立。

## 4. 存量数据迁移

服务启动时执行 `init_db()`：

1. 如果业务表中已有数据且还没有任何里程碑，自动创建 `M1`（状态 active）。
2. 把所有存量数据的 `milestone_id` 指向 M1。
3. 数据库为空时不自建里程碑，由用户手动创建第一个。

迁移过程只做表重建和字段补充，不删除业务数据。

## 5. 后端接口

新增里程碑路由：

- `GET /api/milestones`：列出里程碑及状态、数据量。
- `POST /api/milestones`：创建下一个里程碑；若存在 active 里程碑，同一事务内先冻结。
- `POST /api/milestones/{id}/save`：保存（冻结）指定里程碑，已冻结返回 409。

所有业务接口统一增加必填查询参数 `milestone_id`：

- 读接口只返回该里程碑的数据。
- 写接口先校验里程碑状态，frozen 时返回 409。
- 同步只写入指定且处于 active 的里程碑。
- 报告按选中里程碑的数据生成，标题带上里程碑名称。

## 6. 前端交互

- 顶部工具栏：里程碑下拉、新建里程碑、保存里程碑。
- 选中已保存的里程碑时显示只读提示条。
- 切换里程碑后页面重新挂载并加载对应数据。
- 当前选择保存在 localStorage。
- 只读状态下禁用或隐藏所有写操作：
  - 投递列表：状态勾选、投递日期、批量发消息。
  - BOSS 详情：发送消息。
  - 消息提醒：预览、发送、失败队列重试 / 删除。
  - 设置：同步、清空当前里程碑数据；全局配置仍可修改。
  - 概览、统计、报告：正常查看。

## 8. 测试与验收

- 迁移：旧库数据全部归入 M1，不丢数据。
- 约束：同一里程碑内 encrypt_boss_id 唯一，不同里程碑可以重复。
- 隔离：按 milestone_id 查询只返回对应数据。
- 冻结：active 可写，frozen 写入返回 409。
- 编号：连续创建得到 M1、M2、M3，旧的自动冻结。
- 回归：现有 test/test_database.py 全部通过。
- 前端由用户在浏览器手动验证交互与只读效果。
